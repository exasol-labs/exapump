# Open Questions: add-json-import

speq-plan-pr could not complete this plan without human input. What's done so far is committed on this branch. Reply inline on the PR, or resume with `/speq:plan add-json-import` locally, or re-run `/speq:plan-pr add-json-import` after commenting.

- [ ] **Partial-load reporting has no carrier in the stated `load` signature.** `load` is declared to return `anyhow::Result<Vec<(String, u64)>>`, but the spec requires stdout to list the tables already loaded when a later table fails, and the `Err` arm of that signature carries no counts. Proposed fix (round-2 review): change the signature to `pub async fn load(family: &TableFamily, path: &Path, conn: &mut exarrow_rs::Connection) -> (Vec<(String, u64)>, Option<anyhow::Error>)`, so the partial result survives failure, and print that vector from `src/commands/upload.rs` on both the success and the failure path. Confirm this is the right shape (vs. a dedicated error enum, or a callback) before implementation starts.
- [ ] **`_id` restarts at 1 on every run, so repeated imports corrupt the root/subtable linkage rather than append to it.** `json_tables_core`'s `TableBuffer::new` sets `next_id: 1` per invocation (upstream `json_tables_udf` avoids this by `DROP TABLE ... CASCADE` before reload, which this plan's non-goals rule out). The plan currently promises a repeated run "loads into the existing family" and exits 0, but a second run writes a second `_id = 1` row into the root table with `_parent` values in every subtable now ambiguously matching two parents. Proposed fix (round-2 review): document the limit in the spec and decision log, and require the command to print a stderr warning that `_id` values repeat across runs and family linkage only holds within one run. Confirm whether that warning is sufficient for v1, or whether repeated-run support should be scoped out (or the family should be re-created per run, e.g. `DROP TABLE IF EXISTS ... CASCADE` before load) instead.
