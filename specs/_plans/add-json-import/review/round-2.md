## Premortem

Three failure stories drove this round.

**Story 1. The partial-failure test cannot be written.** The spec requires stdout to list the tables loaded before a failure. `load` returns `anyhow::Result<Vec<(String, u64)>>`, whose error arm carries no counts, and the printing sits in `src/commands/upload.rs`. Routed to `[UNSTATED_ASSUMPTION]`.

**Story 2. The second run silently breaks the family.** `TableBuffer::new` sets `next_id: 1`, so a repeated run restarts `_id` at 1. The root table then holds two rows with `_id = 1`, and every `_parent` value in the subtables matches two parents. The spec requires the repeated run to succeed and decision [7] rests on the linkage columns carrying the relationship. Routed to `[UNSTATED_ASSUMPTION]`.

**Story 3. The partial-failure fixture loses its sabotage target.** plan.md § Verification claims "family order sorts the root last". The sort key is a string, so a top-level property named `shipping`, `tags`, or `user` sorts after the literal `root` and the root is imported first. Routed to `[UNSTATED_ASSUMPTION]`.

## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: plan.md § Decision, the `load` signature and its doc comment; task 2.7, final sentence; task 2.8, final sentence; `upload/json-import/spec.md` § Scenario "Import failure reports the tables already loaded"
- Issue: the partial-load report has no path through the stated interface. `load` returns `anyhow::Result<Vec<(String, u64)>>`. Task 2.7 says "return an error naming the failed table while preserving the per-table counts already collected", but the `Err` arm carries only an `anyhow::Error` and the plan names no carrier for the counts. Task 2.8 then says "On failure, print the tables loaded so far to stdout before returning the error", and that code sits in `src/commands/upload.rs`, which receives only that error. The spec step "stdout MUST list the tables loaded before the failure" is therefore not implementable from the plan, and `partial_family_failure_reports_loaded_tables` cannot be written. An implementer must invent one of three different mechanisms, and two of them move stdout writes into `src/json_tables.rs`, which every other item in plan.md § Patterns keeps free of output.
- Fix: in plan.md § Decision, change the `load` signature so the partial result survives the failure. Declare `pub async fn load(family: &TableFamily, path: &Path, conn: &mut exarrow_rs::Connection) -> (Vec<(String, u64)>, Option<anyhow::Error>)`, and state in its doc comment that the vector holds every table loaded before the error, in family order. Update task 2.7 to return that pair instead of "preserving" counts inside an error. Update task 2.8 to print the returned vector on both the success and the failure path, and to keep every stdout write in `src/commands/upload.rs`.

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: decision-log.md § [7] § Rationale, sentence "The `_id`, `_parent`, `_pos`, and `<name>|object` columns still carry the relationship"; plan.md § Consequences, row "`CREATE TABLE IF NOT EXISTS` and no constraint statements"; `upload/json-import/spec.md` § Scenario "Repeated run loads into the existing family"
- Issue: `_id` is per-run, not per-table. `json_tables_core/src/buffer.rs:114` sets `next_id: 1` in `TableBuffer::new`, and `buffer.rs:136-140` increments it from there, so every invocation restarts the counter at 1. A repeated run against an existing family therefore writes a second row with `_id = 1` into the root table, and every `_parent` value the subtables carry now matches two parent rows. The relationship the decision relies on to justify dropping the constraint statements does not survive the second run. Upstream avoids this: `json_tables_udf/src/source.rs:496` and `json_tables_udf/src/driver.rs:84` issue `DROP TABLE IF EXISTS ... CASCADE` rather than append. The spec scenario requires the repeated run to succeed and exit 0, so the plan mandates the corrupting path and documents nothing about it.
- Fix: in decision-log.md § [7] § Rationale, replace the quoted sentence with the upstream fact that `TableBuffer` restarts `_id` at 1 on every run, so `_id` is unique only within one invocation and `_parent` links only resolve within one invocation. Add the same fact to the `upload/json-import` spec Background as a named limit. Change the spec scenario "Repeated run loads into the existing family" to add the step "*AND* the command MUST print a warning to stderr stating that `_id` values repeat across runs and the family linkage holds only within one run", and add the matching assertion to `repeated_run_appends_to_existing_family` in plan.md § Verification.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Verification, the note on `partial_family_failure_reports_loaded_tables`, sentence "The sabotaged table must be the root, not a subtable, because family order sorts the root last (see § Decision)"
- Issue: the root is not generally last. The sort key is `TablePath::to_string()` compared as a string (`json_tables_core/src/infer.rs:83`), and the root renders as the literal `root` (`json_tables_core/src/contract.rs:223-228`). A top-level property named `shipping`, `tags`, or `user` therefore sorts after `root`, and the root is created and imported first. The note holds only because the fixture's top-level nested properties are `customer` and `items`, and task 2.1 does not pin those names. A later fixture edit silently breaks the test's premise, because a sabotaged first table leaves nothing loaded before the failure.
- Fix: in plan.md § Verification, replace the quoted sentence with "The sabotage target must sort after at least one other table. The fixture's nested properties are `customer` and `items`, both of which sort before the literal `root`, so the root is imported last." Add to task 2.1 that the nested-array-and-object fixture MUST use the property names `customer` and `items`.

## Requirement Quality

#### [COMPLETENESS_GAP] ADVISORY
- Location: plan.md task 2.3, sentence "A table planned from documents that carry properties always holds at least one column outside that set"; decision-log.md § [13] § Decision; `upload/json-import/spec.md` § Scenario "Documents with no properties"
- Issue: the rejection set omits two generated column kinds, so the rule does not match its own stated intent. `json_tables_core/src/infer.rs:317-348` emits a `<name>|object` column and a `<name>|array` column, both typed `SimpleType::Integer` and therefore physical. For the input `[{"a": {}}, {"a": {}}]` the root table carries `_id` plus `a|object`, and the child object table carries `_id` alone. Neither table is key-only under the stated set, so the run creates two tables that hold no document data and exits 0. The spec's own stderr requirement, "no column could be derived from the documents", is the condition that actually holds for this input.
- Fix: in plan.md task 2.3 and decision-log.md § [13] § Decision, widen the rejection set to the generated columns `_id`, `_parent`, `_pos`, and any column whose name ends in `|object` or `|array`. Delete the quoted sentence and replace it with "A table planned from documents that carry a scalar property always holds at least one column outside that set." Add the input `[{"a": {}}]` to the "Documents with no properties" fixture in task 2.1.
