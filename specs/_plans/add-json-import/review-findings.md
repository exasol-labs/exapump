### src/json_tables.rs

#### [CONTEXTLESS_ERROR] Pass-2 buffering failures are reported as file-read failures
- Location: lines 192-206 (`read_documents`), line 286 (`collect_rows`)
- Issue: `read_documents` wraps the entire `for_each_document` call in `failed to read {path}`. That context is correct for pass 1 and for genuine framing or parse errors, but in pass 2 the visitor is `write_document`, so every sink failure is presented to the user as a file-read failure naming the input path. The reachable cases are `Missing writer for path {path}` and `Missing column data for {column}` (json_tables_core `buffer.rs`), the `Expected bool|integer|number|string for {column}` family (`buffer.rs` `set_scalar`), and the array-child-without-parent-id error (`sink.rs` `MissingArrayParentIdPolicy::Error`). None of those is a read failure, so the error states an operation that did not fail and sends the user to inspect the file rather than the document shape. `read_documents`' own doc comment at lines 190-191 states the shared error wording as deliberate, so the defect is in the design as written, not a slip.
- Fix: In src/json_tables.rs, change `read_documents`' closure bound from `FnMut(usize, &serde_json::Map<String, serde_json::Value>) -> json_tables_core::CoreResult<()>` to `FnMut(usize, &serde_json::Map<String, serde_json::Value>) -> anyhow::Result<()>`, take `visit` as `mut visit`, and carry the visitor's error out of band: declare `let mut visit_failure: Option<anyhow::Error> = None;` before the `for_each_document` call, pass a closure that calls `visit(index, document)` and on `Err(error)` stores it in `visit_failure` and returns `Err(json_tables_core::CoreError::msg("document rejected"))`, bind the call's result to `let framing = ...` without `?`, then `if let Some(error) = visit_failure { return Err(error); }` before `framing.with_context(|| format!("failed to read {}", path.display()))`. Update the two call sites: in `plan_family` the closure body stays `stats.record_document(document); Ok(())`, and in `collect_rows` make it `write_document(&mut buffers, document).with_context(|| format!("failed to buffer the documents of {}", path.display()))`.

#### [UNNECESSARY_ALLOCATION] The Arrow bridge clones every numeric column before converting it
- Location: lines 307-312
- Issue: the `Bool`, `Int` and `Double` arms call `v.clone()` on the buffered column and hand the clone to the Arrow builder, which then allocates its own values buffer and validity bitmap and drops the clone immediately. The clone is pure waste, and the `Str` arm at lines 313-316 already avoids the same waste with `StringArray::from_iter`. Measured against the live container: a 21.2 MB, 400,000-row, 5-column NDJSON import peaks at 97 MB RSS (sampled from `/proc/<pid>/status` `VmHWM` while the process ran); each `Vec<Option<i64>>` column in that family is 6.4 MB, so the clone adds one column's worth of transient allocation on top of a family buffer that plan.md § Consequences already accepts as scaling with input size.
- Fix: In src/json_tables.rs `build_record_batch`, replace `BooleanArray::from(v.clone())` in the `ColumnValues::Bool(v)` arm with `BooleanArray::from_iter(v.iter().copied())`, replace `Int64Array::from(v.clone())` with `Int64Array::from_iter(v.iter().copied())`, and replace `Float64Array::from(v.clone())` with `Float64Array::from_iter(v.iter().copied())`. Leave the `ColumnValues::BoolMask(v)` arm exactly as it is, because its `Vec<bool>` is one byte per element and `BooleanArray::from(Vec<bool>)` is what keeps that array free of a validity buffer, which line 318 relies on.

## Expert fixes

### src/json_tables.rs

#### [INFORMATION_LEAKAGE] The physical-column set and order is decided in two modules with nothing pinning their agreement
- Location: lines 133-155 (`build_ddl`), lines 159-163 (`physical_columns`), lines 296-325 (`build_record_batch`)
- Issue: the column list of each `CREATE TABLE` comes from `json_tables_core::ddl::build_sql_schema` and is kept verbatim, because `build_ddl` only rewrites the statement head and splices the upstream body back in at line 150. The column list of each Arrow `RecordBatch` is rebuilt independently by `physical_columns`. The import has no name-based safety net: `import_from_record_batches` serializes the batch to CSV and issues `IMPORT INTO <table> FROM CSV` with no column list (exarrow-rs 0.16.0, `src/import/arrow.rs:686-693`), so Exasol maps fields onto columns strictly by position. The two lists agree today only because both happen to iterate `plan.columns` and filter on `column_sql_type`; nothing enforces it and no test observes it. If the pinned `v0.3` tag is ever moved, or `build_sql_schema` changes which columns it emits or in what order, the import loads values into the wrong columns and stays silent wherever the types are compatible. That is not hypothetical for this feature's output: verified against the live container, `[{"id": 1, "items": []}, {"id": 2, "items": []}]` plans a root table whose three physical columns `"_id"`, `"id"` and `"items|array"` are all `DECIMAL(18,0)`, so any permutation among them would import cleanly and produce wrong data. The existing integration tests only catch a reorder when it crosses a type boundary.
- Fix: In src/json_tables.rs add a `#[cfg(test)] mod tests` with `fn ddl_column_order_matches_record_batch_field_order`, written entirely in-process with no filesystem and no connection. Build `let plans = json_tables_core::infer::StatsCollector::plan_from_documents(&documents);` over a `Vec<serde_json::Map<String, serde_json::Value>>` of `serde_json::json!` documents that together produce a root object table, a nested object subtable, a nested array subtable, a property observed with two different scalar types, and a property observed as an explicit `null`, so that `Primary`, `Alternate` and `NullBitmask` columns all appear. Build the buffers with `let mut buffers = json_tables_core::buffer::ColumnBuffers::new(&plans);` and feed the same documents through `json_tables_core::sink::write_document(&mut buffers, document)`. Call `build_ddl(&plans, "ORDERS", Some("SALES"))`. Then for each `(plan, create)` pair assert that the leading identifier of every line of the CREATE body, in order, equals `sanitize_ident(field.name())` for the corresponding field of `build_record_batch(plan, &buffers).unwrap().schema()`, and assert the two lists have the same length. Parse the CREATE body by taking the lines between the first `(` and the closing `);`, trimming each, and reading the leading double-quoted identifier including its doubled-quote escapes.
