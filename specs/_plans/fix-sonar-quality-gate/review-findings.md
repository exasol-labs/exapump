- `profile.rs` — `init`/`init_profile`, `edit`/`edit_profile`, `prompt_bucketfs`, `edit_bucketfs`, `inquire_port`, `prompt_profile_name`, `prompt_new_password` all reproduce HEAD's prompt strings, defaults, `required` checks, blank-to-`None` rules (`is_empty()`, not `trim().is_empty()`), and default-flag reconciliation order. `make_default.then_some(true)` round-trips through `profile.default.unwrap_or(false)` exactly as HEAD's `if make_default { Some(true) } else { None }` did. **BucketFS port handling confirmed non-retrying** in both `prompt_bucketfs` (`:672-675`) and `edit_bucketfs` (`:907-910`): `parse_port(...).ok_or_else(|| anyhow!("invalid BucketFS port: {}", port_raw))?`, same untrimmed `port_raw` in the message, no `notice`, no loop — matching HEAD's `anyhow::bail!` and decision-log [8]. Two tests pin it.
- `sql.rs` — the `StatementScanner` decomposition is a real abstraction, not a metric-driven split: it owns the seven mutable locals HEAD's loop threaded by hand, and each state's rule is a method. No finding against it.

- `export.rs` — one genuine user-visible behavior deviation found and recorded below (finding 9).

## Standard fixes

### .github/workflows/ci.yml

#### [SWALLOWED_ERROR] Version extraction fails silently and reverts Lever 2
- Location: lines 159-161
- Issue: `run: echo "version=$(grep -m1 '^version' Cargo.toml | sed -E 's/version = "(.*)"/\1/')" >> "$GITHUB_OUTPUT"` discards the exit status of both `grep` and `sed` — `echo` always succeeds, so a non-matching `Cargo.toml` writes `version=` (empty) and the step goes green. The scanner then receives `-Dsonar.projectVersion=` with an empty value, which is exactly the `projectVersion: not provided` state that produced the `NONE` gate status this plan exists to fix. The failure is invisible until the O2 operator check runs after merge. It works against today's `Cargo.toml` (verified: emits `0.11.3`), but nothing enforces that.
- Fix: In `.github/workflows/ci.yml`, rewrite the `Read crate version` step to use a multi-line `run: |` block beginning with `set -euo pipefail`, assign the extracted version to a shell variable, and add an explicit guard that exits non-zero with a message naming `Cargo.toml` when the variable is empty, before writing it to `$GITHUB_OUTPUT`.

### src/commands/export.rs

#### [ASSERTION_FREE_TEST] `build_csv_options_applies_null_value_when_non_empty` asserts nothing about the null value
- Location: lines 422-428 (and 415-420)
- Issue: the test sets `args.null_value = "N/A"` and then asserts only `build_csv_options(&args).is_ok()`. It passes unchanged if the `if !args.null_value.is_empty() { options = options.null_value(...) }` branch at `export.rs:93-95` is deleted outright, so it covers the line without testing the behavior its own name promises. This is the assertion-free-test pattern plan.md § Requirements explicitly bans as a way to move the coverage number. `exarrow_rs::CsvExportOptions` exposes `pub null_value: Option<String>`, `pub column_separator: char`, `pub column_delimiter: char` and `pub with_column_names: bool`, so the real assertion is available.
- Fix: In `src/commands/export.rs`, change `build_csv_options_applies_null_value_when_non_empty` to bind the returned options and assert `options.null_value == Some("N/A".to_string())`. Change `build_csv_options_succeeds_without_compression` to assert `options.null_value == None`, `options.column_separator == ','`, `options.column_delimiter == '"'` and `options.with_column_names == true` instead of `is_ok()`.

#### [MISSING_BOUNDARY_TEST] `--compression` + CSV validation now runs after source resolution, changing which error the user sees
- Location: lines 282-300 (`run`), 83-86 (`build_csv_options`)
- Issue: at HEAD, `run` rejected `--compression` with `--format csv` *before* resolving the export source. `build_csv_options` now owns that check and is called only inside the `ExportFormat::Csv` match arm at `:289`, i.e. after `resolve_export_source(&args)?` at `:283`. When a user passes `--compression --format csv` with neither `--table` nor `--query`, the reported error changes from `--compression is only supported for Parquet format` to `either --table or --query must be provided`. plan.md § Non-Goals states "No change to user-visible CLI behavior"; the implementation notes record this reordering but leave it unfixed. No test in `tests/export_test.rs` or in the new unit module pins the precedence, which is why it was invisible.
- Fix: In `src/commands/export.rs`, move the compression rejection out of `build_csv_options` into a new `fn reject_compression_for_csv(args: &ExportArgs) -> anyhow::Result<()>` and call it as the first statement of `run`, before `resolve_export_source`. Keep the message `--compression is only supported for Parquet format` byte-identical. Add a unit test named `compression_with_csv_is_rejected_before_the_missing_source_error` that builds `ExportArgs` with `compression: Some(Compression::Snappy)`, `format: ExportFormat::Csv`, and neither `table` nor `query`, calls the new function, and asserts the compression message. Update `build_csv_options_rejects_compression` to target the new function.

#### [TOO_MANY_ARGUMENTS] Four new export helpers take 5-6 parameters, one of them redundant
- Location: lines 127-134 (`export_csv`, 6 params), 161-167 (`write_parquet_batches`, 5), 206-212 (`export_parquet_split`, 5), 264-270 (`export_parquet`, 5)
- Issue: every function this task extracted exceeds the ≤3 guardrail. `export_csv`'s `with_header: bool` is additionally redundant: `run` passes `!args.no_header` at `:296` while `build_csv_options` has already encoded the same decision as `options.with_column_names` at `:91`. Two places now hold one decision, and `CsvExportOptions.with_column_names` is a public field the callee can read directly. `export_parquet_split` and `export_parquet` share an identical `(base_path, limits, compression)` trailing triple, which is a cohesive "where and how the parquet output is written" group rather than an arbitrary bundle.
- Fix: In `src/commands/export.rs`, delete the `with_header: bool` parameter from `export_csv` and read `options.with_column_names` inside it when constructing `SplitCsvWriter`; drop the corresponding argument at the `run` call site. Then introduce `struct ParquetTarget<'a> { base_path: &'a Path, limits: SplitLimits, compression: Option<&'a Compression> }` and change `export_parquet`, `export_parquet_split` and `write_parquet_batches` to take `conn`/`batches` plus that struct, so each sits at 3 parameters or fewer.

#### [INLINE_COMMENT] Rationale lives in in-body comments inside private functions
- Location: `src/commands/export.rs` lines 213-214, 224-226, 235; `src/commands/sql.rs` lines 201-202
- Issue: `export_parquet_split` carries three in-body comment blocks ("Obtain the Arrow schema by running a zero-row query…", "Set batch_size to match max_rows…", "Ensure the output path exists…") and `StatementScanner::scan_script_body` carries one ("Lone `/` line terminator: drop the trailing newline…"). The guardrails forbid inline comments; the rationale itself is non-obvious and worth keeping, so it belongs in each function's doc comment where it is stated once at the interface rather than buried mid-body.
- Fix: In `src/commands/export.rs`, delete the three in-body comment blocks in `export_parquet_split` and add a doc comment above the function that states, in prose, why a zero-row schema query is needed, why `batch_size` is aligned to `max_rows`, and why an empty result still writes an output file. In `src/commands/sql.rs`, delete the in-body comment in `StatementScanner::scan_script_body` and add a doc comment above the method explaining the lone-`/` terminator rule and the trailing-newline drop.

### src/commands/interactive.rs

#### [TOO_MANY_ARGUMENTS] `dispatch_line` takes five parameters, four of them the REPL's session state
- Location: lines 199-205
- Issue: `dispatch_line(line, conn, rl, buffer, format)` exceeds the ≤3 guardrail. Four of the five (`conn`, `rl`, `buffer`, `format`) are exactly the mutable locals `run` holds across loop iterations at `:225-230`, so they are one cohesive object rather than five independent inputs. The five-way `&mut` threading is also why the function is unreachable from a unit test, which is why task 2.6 could only test `classify_line`.
- Fix: In `src/commands/interactive.rs`, introduce `struct ReplSession { conn: exarrow_rs::Connection, rl: DefaultEditor, buffer: String, format: InteractiveFormat }`, construct it in `run` from the values currently held as locals, and convert `dispatch_line` into `async fn dispatch_line(&mut self, line: &str) -> ControlFlow` on that struct. Update `run`'s loop to read the prompt from `session.buffer.is_empty()` and to call `session.dispatch_line(&line).await`.

### src/commands/profile.rs

#### [BOOLEAN_FLAG_PARAMETER] `ProfilePrompter::text` takes a `required` flag that selects its branch
- Location: lines 406-417
- Issue: the provided method `text(&mut self, label, default, required: bool)` branches on `required` at `:413` to decide whether to run the empty-check. Update all fifteen call sites to the matching method, and rename the tests `text_rejects_a_blank_answer_when_the_field_is_required` and `text_accepts_a_blank_answer_when_the_field_is_optional` to target `required_text` and `text` respectively.

### src/commands/sql.rs

#### [OUTPUT_PARAMETER] `render_result` returns its separator state through a mutated argument
- Location: lines 437-452, caller at 528 and 541-546
- Issue: `render_result(batches, format, first_select: &mut bool, writer)` both writes output and mutates `*first_select = false` at `:446` so the caller's next call behaves differently. `run` never reads `first_select` itself (declared `:528`, passed only at `:544`), so the flag exists purely to carry state back out of the callee — the output-parameter pattern the guardrails prohibit. It also pushes the function to four parameters.
- Fix: In `src/commands/sql.rs`, introduce `struct ResultRenderer { rendered_any: bool }` with `fn new() -> Self` and `fn render(&mut self, batches: &[RecordBatch], format: &OutputFormat, writer: &mut impl Write) -> anyhow::Result<()>` holding the current `render_result` body with `*first_select` replaced by `self.rendered_any`. Delete the free `render_result` function, construct one `ResultRenderer` in `run` in place of the `first_select` local, and call `renderer.render(...)`. Retarget the three `render_result_*` unit tests at the new method, keeping their assertions unchanged.

#### [SELECTOR_ARGUMENT] `execute_one` takes the statement type that picks its branch
- Location: lines 485-512, caller at 533 and 536
- Issue: `execute_one`'s entire body is `match stmt_type { … }`, so `stmt_type` is a pure branch selector. `run` computes `let stmt_type = StatementType::from_sql(stmt);` at `:533` and uses it at `:536` and nowhere else, so the parameter buys nothing. The sibling function `interactive::execute_and_report` (`interactive.rs:320`) already derives the type internally from `stmt`, so the two files disagree on the same call shape for no reason.
- Fix: In `src/commands/sql.rs`, remove the `stmt_type: StatementType` parameter from `execute_one` and compute `StatementType::from_sql(stmt)` as the `match` scrutinee inside it. Delete the `let stmt_type = …` binding at `run`'s `:533` and update the call at `:536` to `execute_one(&mut conn, stmt.as_str()).await`.

### src/commands/interactive.rs

#### [INFORMATION_LEAKAGE] The per-`StatementType` execution rule now lives in two modules
- Location: `interactive.rs:315-343` (`execute_and_report`) against `sql.rs:485-512` (`execute_one`); `interactive.rs:151-153` (`row_count`) against `sql.rs:401-403` (`total_rows`)
- Issue: `execute_and_report` and `execute_one` encode the same four decisions — `Query` always fetches, `Dml` and `Ddl` go through `execute_update`, and an `Execute` result is fetched only when `result_set.is_stream()`. That last rule is the non-obvious one, and it is now written twice with nothing enforcing agreement; a change to how Exasol reports streaming results would have to be made in both files or the REPL and the script runner would silently diverge. `sql::StatementOutcome` was built to be exactly the format-neutral carrier `interactive` needs — it names rows, rows-affected and OK, and carries no `OutputFormat` coupling — so the notes' three reasons for rejecting reuse apply to `sql::render_result` (no `Table` variant, `first_select` semantics) and to a now-expired plan-phase constraint, not to `execute_one`. Separately, `interactive::row_count` and `sql::total_rows` are the same one-line body in two modules, with `total_rows` newly added by task 2.4 while `row_count` already existed.
- Fix: In `src/commands/sql.rs`, change `execute_one` and `enum StatementOutcome` (and its three variants) to `pub(crate)`. In `src/commands/interactive.rs`, rewrite `execute_and_report` to call `super::sql::execute_one(conn, stmt).await?` and `match` the returned `StatementOutcome`: `Rows(batches)` calls `print_result(&batches, format)`, `RowsAffected(n)` prints `rows_affected_line(n)`, `Ok` prints `"OK"`. Delete `interactive::row_count` and have `print_result` call `super::sql::total_rows`. Do this only after landing the `[SELECTOR_ARGUMENT]` fix above so `execute_one` derives the statement type itself. Then re-run the byte-level REPL differential check the task 2.5 notes describe (scripted session against a HEAD-built binary, `sha256` of `stdout`, `stderr` normalized for the `Session:` token) and confirm both hashes still match; a passing test suite alone is not sufficient evidence here, because `tests/cli_test.rs` drives the REPL only with `EXECUTE SCRIPT`.
