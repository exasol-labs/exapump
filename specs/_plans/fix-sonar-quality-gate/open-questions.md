# Open Questions: fix-sonar-quality-gate

speq-plan-pr could not complete this plan without human input. What's done so far is committed on this branch (`feat/fix-sonar-quality-gate`). Round-1 review found 5 blockers; all 5 were resolved by a revision pass. Round-2 review (bounded to 2 rounds) found 3 new blockers introduced or exposed by that pass. Reply inline on the PR, or resume with `/speq:plan fix-sonar-quality-gate` locally, or re-run `/speq:plan-pr fix-sonar-quality-gate` after commenting.

- [ ] **Task 1.1b measures the wrong quantity.** It filters `llvm-cov --json` regions on `.[5] == 0` (the file id) instead of `.[4] == 0` (the execution count), and even corrected, a region count is not a line count — the plan's 194-line target and its gate formula are both in line units. Measured on a probe crate: the plan's expression reports 4-5 per function where the correct uncovered-line count is 0-1. As written, the gate that exists to validate the 194-line assumption passes unconditionally, leaving that assumption untested. Fix direction from review: switch to a line-level measurement — either compute uncovered lines from `files[].segments` restricted to each function's line range, or read per-function uncovered-line counts off a generated `cargo llvm-cov --html` report. Full detail: `specs/_plans/fix-sonar-quality-gate/review/round-2.md` § Feasibility finding 1.

- [ ] **The recorded cognitive-complexity hand-count method (task 1.7) undercounts.** Calibrated against two functions SonarCloud has already scored, the method reproduces `profile::show` (Sonar 19) exactly but yields 17 for `profile::init` against Sonar's actual 22 — missing the +1 per bare `else` that the method's rule list omits. Since this hand count is the *only* in-loop completion gate for all 7 Phase 2 refactor tasks, undercounting lets a task be marked done while still above the real threshold — caught only after the PR analysis runs, when the PR can no longer merge. Two smaller correctness issues in the same rule list also risk false failures (nesting increment wrongly applied to `else if` and to `&&`/`||` sequences, which SonarSource's spec excludes). Fix direction from review: rewrite the rule list per round-2's corrected spec and require the implementer to reproduce both calibration numbers (19 and 22) as a self-check before counting anything else. Full detail: round-2.md § Requirement Quality finding 1.

- [ ] **The Phase 1 coverage-feasibility gate is prose, not a task.** It sits as a paragraph between checkbox tasks 1.1b and 1.2, stating a hard precondition ("Phase 2 must not start until this is answered") and real work (recompute targets if R < 194, rewrite two Requirements rows, amend decision-log.md), but has no checkbox, so `/speq:implement` has nothing to schedule or verify — the gate can be silently skipped. Fix direction from review: split into two checkbox tasks, 1.1c ("compare R against 194, record the outcome") and 1.1d ("conditional on R < 194, recompute and rewrite the targets"), both in Group A, with the Group A→Group C1 dependency stating Phase 2 cannot begin until 1.1c or 1.1d is checked. Full detail: round-2.md § Task Breakdown finding 1.

## Advisory findings carried forward (non-blocking, worth a look)
- R (the 194-line target's coverage-yield sum) may over-count: functions task 1.1b sums include `inquire`/`rpassword` call bodies that task 2.2's design actually relocates into `TerminalPrompter`, where they stay uncovered.
- The 85% coverage target is partly self-satisfying: `sonar.sources=src` means new `#[cfg(test)]` modules inside `src/` count as covered source lines, so a large `ScriptedPrompter` test module raises the number without covering production logic. No requirement row currently distinguishes the two.
- Task 2.2's `notice` message enumeration lists 3 of 5 retry messages (`profile.rs:535,542` missing).
- Task 2.2 vs. the Patterns row disagree on whether `remove` and `prompt_password_for` (two more uncovered functions with their own `is_terminal` guards) are in scope for the trait conversion.
- Task 2.2's plan to consolidate `prompt_bucketfs`/`edit_bucketfs` into one function risks a shallow, multi-flag abstraction — the two diverge on prompt text, defaults, and decline behavior across 4 axes, and no existing test would catch a regression.
- Two prose-quality nits: the "194" figure is reused for both a test count (actually 179, not 194) and a line-coverage target in the same document; and the plan Summary's first sentence still exceeds the 25-word cap and hedges "82.46%" as "roughly 82%".
