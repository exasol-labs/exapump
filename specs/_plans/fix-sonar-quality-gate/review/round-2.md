## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `plan.md` § Implementation Tasks task 1.1b; the Phase 1 coverage-feasibility gate paragraph that follows it; `decision-log.md` [7] § Gate
- Issue: the command that produces R measures the total number of coverage regions per function, not the number of uncovered lines. Task 1.1b runs `jq -r '.data[0].functions[] | select(...) | [(.name), ([.regions[] | select(.[5] == 0)] | length)] | @tsv'`. In the `llvm-cov` JSON export a region is `[line_start, col_start, line_end, col_end, execution_count, file_id, expanded_file_id, kind]`; index 5 is the **file id**, index 4 is the execution count. For a function defined in one file with no macro expansion every region has `file_id == 0`, so the filter matches all of them. Measured on a purpose-built probe crate with `cargo llvm-cov 0.8.7 --json`: a fully covered test function reported **4** under the plan's expression and **0** under `select(.[4] == 0)`; a partly covered function reported **5** versus the correct **1**. Two consequences, both fatal to the gate. First, R is the total region count of the nine named functions, a number certain to clear 194, so the gate that exists to test the 194 assumption passes unconditionally and the round-1 failure mode is untouched. Second, even after correcting the index, a count of uncovered *regions* is not a count of uncovered *lines*: 194 is derived in line units (`611 * (0.70 - 0.383)`), and the gate's recomputation formula `(coverable - uncovered + R) / coverable` is in line units too. The probe shows a one-line function carrying 5 regions, so the units differ by a large and variable factor. A third, smaller defect: `.name` emits the v0-mangled symbol (`_RNvCs..._8covprobe9untouched` in the probe), not `init`/`edit`, and a naive match on `edit` also matches `edit_bucketfs`.
- Fix: In `plan.md` task 1.1b, replace the `--json`/`jq` approach with a line-level measurement. Use `cargo llvm-cov --json --output-path /tmp/cov-baseline.json` and compute per-function uncovered lines from the `files[].segments` array restricted to each function's line range, or simpler, run `cargo llvm-cov --html --output-dir /tmp/cov-baseline-html` and read the per-function uncovered-line counts from the generated `profile.rs` page. State explicitly that R is a count of **uncovered source lines**, in the same unit as 194 and as the gate's `(coverable - uncovered + R) / coverable` formula. Add one sentence telling the implementer that `llvm-cov` function names are v0-mangled and must be matched on the demangled suffix, so `edit` is not confused with `edit_bucketfs`. Update `decision-log.md` [7] § Gate to name the same unit.

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: `plan.md` § Requirements rows "Overall coverage" and "`profile.rs` coverage"; task 3.2; `sonar-project.properties` line `sonar.sources=src`
- Issue: the 85% target is partly self-satisfying and the plan never says so. `sonar-project.properties` sets `sonar.sources=src` and `sonar.tests=tests`, and every unit test this plan adds lives in a `#[cfg(test)]` module inside `src/`. `cargo llvm-cov` instruments those modules, so their bodies enter the lcov report as `src/` lines that are 100% covered by definition — the probe crate confirms the test function itself appears in `functions` with full coverage. - Fix: Add one sentence to `plan.md` § Requirements under the coverage rows stating that `#[cfg(test)]` modules inside `src/` count as covered source under `sonar.sources=src`, and that the Phase 1 baseline and every later measurement are compared on the same basis. Alternatively add `sonar.exclusions` or a `cargo llvm-cov` region filter to task 1.6 that removes `#[cfg(test)]` blocks from the report, and state which choice was made.

## Requirement Quality

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: `plan.md` task 1.7 (the recorded counting method); § Implementation Tasks Phase 2 preamble step 1; § Verification/Checklist row "Cognitive complexity"
- Issue: the hand-count method that replaced round 1's unverifiable criterion disagrees with SonarSource's own measurement of this codebase, and it is now the only in-loop completion gate for all seven Phase 2 tasks. Task 1.7 records: "adds 1 for each `if`, `else if`, `match`, `loop`, `while`, `for`, `catch`-equivalent (`?` does not count), and each `&&`/`||` sequence; adds the current nesting depth as an extra increment for each of those that is nested inside another; and adds 1 per `break`/`continue` with a label." Calibrated against two functions Sonar has already scored:
  - `profile::show` (`profile.rs:220`, Sonar 19) — one `match` at depth 0 plus nine `if let`/`if` at depth 1 gives `1 + 9*2 = 19`. The method reproduces Sonar exactly. This function contains no `else`.
  - `profile::init` (`profile.rs:370`, Sonar 22) — the method yields **17**: eight `if` (one nested, so 9 points), five `match` (5), one `||` sequence (1), one `for` nested inside an `if` (2). The five bare `else` blocks at `:417`, `:428`, `:441`, `:472` and `:478` add the missing 5 and land exactly on Sonar's 22.

  The bare `else` increment is missing from the recorded method, and its omission under-counts by one per `else`. Under-counting is the dangerous direction: a Phase 2 implementer can hand-count a refactored function at 14, mark the task done per the preamble's "a function above the threshold fails the task", and leave a function Sonar scores at 18 still open. Nothing catches it until operator step O1, after the PR analysis, on a PR that then cannot merge. Two further deviations from the published SonarSource specification point the other way and will cause false failures: the nesting increment does not apply to `else if`, and does not apply to `&&`/`||` sequences at all, yet the method's "each of those" applies it to both. The method is also silent on two constructs that appear throughout this codebase — closures (which raise the nesting level for control flow inside them) and recursion — so an implementer counting `execute_statement` or `split_statements` has no rule to follow for either.
- Fix: In `plan.md` task 1.7, rewrite the recorded counting method to state: (a) `+1` for each `if`, `else if`, **`else`**, `match`, `loop`, `while`, `for`, and each sequence of `&&`/`||`; (b) `+1` per recursive call cycle; (c) `+1` per labeled `break`/`continue`; (d) the nesting increment applies **only** to `if`, `match`, `loop`, `while`, `for` and closure bodies — never to `else`, `else if`, boolean-operator sequences or labeled jumps; (e) the nesting level is raised by `if`, `else`, `match`, loops and closure bodies. Add the two worked calibration examples to the same task as a self-check the implementer must reproduce before counting anything else: `profile::show` must count to 19 and `profile::init` to 22, matching the § Design/Context table. State that a method that fails either calibration is wrong and must be corrected before any Phase 2 task is marked done.

## Design Depth

#### [SHALLOW_DESIGN] ADVISORY
- Location: `plan.md` task 2.2, the sentence "Consolidate the near-duplicate BucketFS prompt logic shared by `prompt_bucketfs` and `edit_bucketfs` into one function over the trait"
- Issue: the two functions diverge on four axes, so a single consolidated function needs a mode parameter for each, and `/speq:design-philosophy` treats a configuration parameter as a decision the module declined to make. `prompt_bucketfs` (`profile.rs:554`) opens with `"Configure BucketFS? (needed for \`exapump bucketfs\` commands)"` and returns all-`None` on decline; `edit_bucketfs` (`:809`) opens with `"Edit BucketFS settings?"` and returns the current values on decline. Defaults differ: `Some("")`, `DEFAULT_BFS_PORT` and `"default"` versus the profile's current values. Password prompts differ in wording and meaning: `"BucketFS write password (blank to skip): "` and `"(blank = same as write password): "` versus `"BucketFS write password (blank = clear): "`. Decision [8] and § Verification/Manual Testing both require byte-identical output, so all four divergences must survive the merge, and the result is one function carrying three or four mode flags — a shallower abstraction than the two it replaces. The safety net does not cover the risk either: `grep -n "blank to skip\|blank = clear\|Configure BucketFS\|Edit BucketFS" tests/profile_test.rs` returns nothing, so no existing test would catch a prompt-string regression introduced by the consolidation.
- Fix: In `plan.md` task 2.2, replace the consolidation instruction with one that names what is actually shared: extract only the port-parse-and-validate step and the blank-to-`None` mapping into helpers over the trait, and keep `prompt_bucketfs` and `edit_bucketfs` as separate callers that own their own prompt strings, defaults and decline behavior. Add to the same task the requirement that `ScriptedPrompter` tests assert the recorded label sequence for both flows, since no test in `tests/profile_test.rs` covers those strings today.
