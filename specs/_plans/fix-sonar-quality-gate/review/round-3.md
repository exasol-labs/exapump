## Feasibility

#### [UNSTATED_ASSUMPTION] BLOCKER
- Location: `plan.md` task 1.1b — the reconciliation self-check and the `cargo llvm-cov --html` cross-check
- Issue: task 1.1b's mandatory self-check fails on the file it exists to measure, and it fails for a script that is correct. The self-check reads: "the count of zero-count lines over the whole file must equal `f["summary"]["lines"]["count"] - f["summary"]["lines"]["covered"]`. A mismatch means the segment rule is wrong, and every per-function number under it is wrong." I ran the plan's script verbatim against `cargo llvm-cov --bin exapump --json` on this repository. For `src/commands/profile.rs` it reports **604** zero-count lines against a JSON summary of **611** uncovered — a mismatch that condemns the script. It mismatches on 13 of 14 source files (`main.rs` 42 against 64, `split.rs` 29 against 31, `bucketfs.rs` 230 against 256). The script is not wrong: it reproduces llvm-cov's **lcov** line mapping exactly on all 14 files, identical line sets and identical zero/non-zero verdicts. The two llvm-cov outputs use different line rules, and the plan compares one against the other. The named fallback fails the same way: `cargo llvm-cov --html` renders the report-side rule (611), so "counting the zero-count lines inside each function's line range on that page must reproduce the script's numbers" cannot hold either. The implementer is left with a correct measurement the plan tells them to discard, and two cross-checks that disagree with it by construction. The same split has a second consequence the plan never states: Sonar consumes the lcov file, so Sonar's `profile.rs` denominator is 604 lines, while `cargo llvm-cov --summary-only` — the command every § Requirements row names — reports against 611.
- Fix: In `plan.md` task 1.1b, source the per-line counts from the lcov file instead of from `files[].segments`. Read `DA:<line>,<hits>` records for `src/commands/profile.rs` out of the `/tmp/lcov-baseline.info` that task 1.1 already writes, and bucket each line into the function whose `FN:<line>,<mangled-name>` record carries the greatest start line at or below it; this uses llvm-cov's own line rule and needs no reimplementation. Replace the self-check with one internal to that file: the count of zero-hit `DA` records must equal `LF - LH` for the same `SF:` block. Add one sentence stating that `summary.lines.count` in the JSON export uses a different line rule from the lcov export — 611 against 604 for `profile.rs` on `cargo-llvm-cov` 0.8.7 — so the two are never compared. Delete the sentence making `cargo llvm-cov --html` a check that "must reproduce the script's numbers", and keep it only as an eyeball check. Add one sentence to `plan.md` § Requirements stating that both coverage rows are read from `cargo llvm-cov --summary-only` on the report-side rule, and that Sonar's own figure is computed on the lcov rule and runs about one point apart on `profile.rs`.

## Requirement Quality

#### [AMBIGUOUS_REQUIREMENT] BLOCKER
- Location: `plan.md` § Requirements, the paragraph "Both coverage rows count test code as source"; task 1.1c; task 1.1d's `(coverable - uncovered + R) / coverable` formula; tasks 3.1 and 3.2
- Issue: the round-2 advisory fix discloses test-code inflation and then asserts a comparability that its own plan makes impossible. The paragraph requires "every figure compared against these two rows is read on the same basis: the task 1.1 baseline, the task 1.1b per-function counts, the per-file check in each Phase 2 task, and the task 3.2 re-measurement all come from `cargo llvm-cov` over the same target set". Same tool and same target set is not the same basis. `src/commands/profile.rs` carries no `#[cfg(test)]` module today, and tasks 2.2 and 3.1 put one there — `ProfilePrompter`, `ScriptedPrompter` and the whole init/edit test suite, which task 2.2 requires stay private to the module. Those lines land in `sonar.sources=src`, are ~100% covered by construction, and enter both the numerator and the denominator that the requirement rows measure. Measured on files that already have such a module: `src/commands/sql.rs` reports 74.9% while its production half is 50.9%, its test module contributing 356 measured lines all covered; `src/config.rs` reports 94.9% against 76.3% production. Applied to `profile.rs`, a 400-line test module alone moves the file from 38.3% to about 63% and TOTAL from 82.46% to about 84.1% without covering one production line — roughly 120 of the 194 lines the `profile.rs` row demands and roughly 1.6 of the 2.5 points the overall row demands, free. The arithmetic that the round-2 blocker fixes rest on inherits the defect: task 1.1c compares R against 194, derived from `coverable = 611` measured before the test module exists, and task 1.1d's formula names a single `coverable` while two different values apply — the baseline one at derivation time and an inflated one at verification time. Nothing in the plan says which governs.
- Fix: In `plan.md` § Requirements, replace the sentence beginning "It requires instead that every figure compared against these two rows" with a rule that survives the inflation: state that the `profile.rs coverage` row is evaluated over the file's baseline coverable line set alone — the lines task 1.1 records — with every line added by this plan's `#[cfg(test)]` module excluded from both numerator and denominator, and that the `Overall coverage` row is evaluated the same way against the task 1.1 baseline `lines_to_cover`. In task 1.1d, name the `coverable` the formula uses as the task 1.1 baseline value and state that the achieved figure is computed on that same denominator. Add to tasks 3.1 and 3.2 one verification step that cannot be inflated: re-run the task 1.1b measurement and require the uncovered-line count over the nine functions R was summed from to have fallen by at least the R the gate recorded, and record both counts in the implementation notes.

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: `plan.md` task 2.2, "Extract only what is genuinely shared: the port parse-and-validate step (including its retry `notice`) and the blank-to-`None` mapping, as helpers over the trait"
- Issue: the round-2 advisory fix instructs a user-visible behavior change that the plan's Non-Goals and decision [8] forbid. Neither BucketFS function retries. `prompt_bucketfs` (`profile.rs:585-588`) and `edit_bucketfs` (`:853-856`) both hard-fail on an invalid port with `anyhow::bail!("invalid BucketFS port: {}", port_raw)`. The retry-with-`notice` loops live somewhere else entirely: `inquire_port` (`:504-515`) and `edit`'s own port loop (`:702-711`), neither of which is BucketFS. The alternative reading is no better: a single helper serving all four call sites needs a retry-or-bail mode flag, which the same paragraph rejects two sentences earlier as "one function carrying four mode flags is a shallower abstraction than the two it replaces".
- Fix: In `plan.md` task 2.2, delete "(including its retry `notice`)" from the shared-helper sentence. Add one sentence stating that `prompt_bucketfs` (`profile.rs:585-588`) and `edit_bucketfs` (`:853-856`) keep their current hard failure `anyhow::bail!("invalid BucketFS port: {}", port_raw)` with no retry, that the retry-with-`notice` loops belong only to `inquire_port` (`:504-515`) and `edit`'s port loop (`:702-711`), and that the shared helper is the parse-and-validate step alone with each caller owning its own failure behavior.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: `plan.md` task 2.2, "`text` renders `"{label}:"` and applies the `required` empty-check, reproducing today's `inquire_text` exactly"
- Issue: two decisions move out of one function and into every implementation of the trait. Label rendering and the `required` empty-check with its `"{} is required"` failure are validation, not I/O, yet the design puts them behind the seam. `TerminalPrompter` and `ScriptedPrompter` must then implement both identically with nothing enforcing the agreement — the back-door leakage `/speq:design-philosophy` names. A `ScriptedPrompter` that returns queued answers without the empty-check gives green tests for a branch production still takes, which is the one failure mode this whole seam exists to prevent.
- Fix: In `plan.md` task 2.2, state that label rendering and the `required` empty-check live in exactly one place — either a default method on `ProfilePrompter` that both implementations inherit, or a free function both call — so `ScriptedPrompter` cannot diverge from `TerminalPrompter` on either, and that the trait method implementations carry only the prompting.
