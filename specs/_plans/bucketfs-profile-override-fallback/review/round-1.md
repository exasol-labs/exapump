# Plan Review Findings: bucketfs-profile-override-fallback (round 1)

## Summary
- Axes checked: 6/6
- Total findings: 9 (Blockers: 2, Advisory: 7)
- Intent Fidelity blockers: 0

## Premortem

Three failure stories, written as if the plan already shipped and failed.

1. **The default invocation broke.** The implementer coded task 2.2 straight from the Architecture diagram. The diagram has no branch for "no `--bfs-host`, no `--profile`, and a default profile resolves". `exapump bucketfs ls` with a single configured profile now exits with the both-remedies error. No test caught it, because every test in `tests/bucketfs_test.rs` passes `--profile bfs`. Routed to Requirement Quality as `[COMPLETENESS_GAP]`.
2. **A misconfiguration turned silent.** A user with two `default = true` profiles ran `exapump bucketfs ls --bfs-host node2`. `find_default_profile` returned the "Multiple default profiles found" error. Branch 4 swallowed it and connected with the BucketFS defaults instead. The user spent an hour on an empty listing from the wrong bucket. Routed to Requirement Quality as `[REQUIREMENT_CONFLICT]`.
3. **The fix did not unblock the caller.** The defaults base sets `validate_certificate` to `true`. Every Exasol BucketFS reached in the reported scenario presents a self-signed certificate. The `No profiles found in config` error became a TLS validation error. Routed to Feasibility as `[UNSTATED_ASSUMPTION]`.

## Intent Fidelity

Checked and cleared: the widening from "host plus write password" to "host plus any BucketFS credential" adds `--bfs-read-password` as an alternative trigger. It is a superset of the issue's rule, it breaks no invocation that the issue's literal rule would allow, and decision-log entry [1] records the reasoning. Also cleared: keeping profile inheritance for a host-only run matches the issue's own instruction to "fall back to `find_default_profile` only when the overrides are incomplete". Also cleared: the write-password-supplies-read-credential ordering, which decision-log entry [4] ties to the issue's own repro command `bucketfs ls`.

#### [SCOPE_REDUCTION] ADVISORY
- Location: plan.md § Design > Context, the `**Goals**` bullet, and § Impact
- Issue: the goal reads "make an override-only BucketFS invocation succeed without a config file, and make it resolve to the same connection on every machine". The second half is false for the host-only case. Branch 3 takes `bucket`, `port`, `tls`, and `validate_certificate` from an unrelated default profile, and branch 4 takes them from the BucketFS defaults. `exapump bucketfs ls --bfs-host h` therefore still resolves to a different connection on a machine with a config than on a machine without one. That is the issue's secondary concern, and the plan states no boundary on how far it fixes it.
- Fix: In plan.md § Design > Context, change the second goal to "make an override-only invocation that carries a credential resolve to the same connection on every machine". Add one sentence to plan.md § Impact stating that a host-only run without a credential still inherits `bfs_tls`, `bfs_validate_certificate`, `bfs_bucket`, and `bfs_port` from an unrelated default profile, and that issue #46's secondary concern stays open for that case. Add the same boundary to decision-log.md entry [2] under **Rationale**.

## Feasibility

#### [UNSTATED_ASSUMPTION] ADVISORY
- Location: plan.md § Impact (final paragraph of item 1), § Implementation Tasks tasks 3.3 and 3.4
- Issue: the defaults base sets `validate_certificate` to `true`. An Exasol BucketFS in the supported test setup presents a self-signed certificate, so an override-only run fails TLS validation unless the caller adds `--bfs-validate-certificate false`. Three consequences follow. First, plan.md § Impact states "This fixes exapump issue #46 and unblocks `lakehouse-engine-rs` `deploy/scripts/install.sh`" as fact, with no evidence that the external script passes that flag. Second, task 3.3 and task 3.4 name no `--bfs-validate-certificate false` argument, while the § Manual Testing commands for the same behavior do carry it. Third, task 3.4 removes the profile from the resolution path, so the profile's `bfs_validate_certificate = false` no longer reaches the connection. An implementer who copies `write_bfs_config` and drops the flag gets a TLS failure and no signal about which assertion actually failed.
- Fix: In plan.md § Impact, replace the `lakehouse-engine-rs` claim with "This fixes exapump issue #46. A caller against a BucketFS with a self-signed certificate MUST add `--bfs-validate-certificate false`." In plan.md § Implementation Tasks, append "Pass `--bfs-validate-certificate false`, because the defaults base enables certificate validation" to task 3.3 and to task 3.4.

## Requirement Quality

#### [REQUIREMENT_CONFLICT] BLOCKER
- Location: plan.md § Design > Architecture, branch `host, no default profile ──▶ BfsConnection::with_defaults(host)`; decision-log.md entry [2]; spec delta `cli/bucketfs-command-structure` § Background, bullet 4
- Issue: `src/config.rs::find_default_profile` fails for three distinct reasons: zero profiles ("No profiles found in config"), two or more profiles with no default ("No default profile set. Use `exapump profile add <name> --default` ..."), and two or more profiles with more than one default ("Multiple default profiles found: ..."). Branch 4 treats all three as "no default profile" and returns the defaults base. Two recorded scenarios forbid that. `config/profiles/Multiple default profiles is an error` states "the CLI MUST exit with a non-zero code" and "stderr MUST list the conflicting profile names". `config/profiles/Multiple profiles without default is an error` states "the CLI MUST exit with a non-zero code" and "stderr MUST suggest adding `default = true` to one profile". Both trigger on "WHEN exapump resolves connection parameters", which the `bucketfs` command does. Decision-log entry [2] justifies the branch with "This branch only fires where the command already exits non-zero, so it can break no working invocation". The exit code is not the requirement. The requirement is the named diagnostic, and the plan deletes it for the two misconfiguration cases. Branch 2 raises the same conflict from the other side, because it consults no config at all when a host and a credential are present. No delta narrows either recorded scenario.
- Fix: In plan.md § Design > Architecture, change branch 4 to `host, config holds zero profiles ──▶ BfsConnection::with_defaults(host)`, and state in the paragraph below the diagram that every other `find_default_profile` error propagates unchanged. Make the same change to bullet 4 of the spec delta `cli/bucketfs-command-structure` § Background: "Otherwise, `--bfs-host` alone selects the BucketFS defaults when the config holds zero profiles. Any other profile-resolution failure MUST propagate." Add a `DELTA:NEW` scenario to `cli/bucketfs-command-structure` named "Ambiguous default profile still fails a host-only run", with GIVEN a config holding two profiles that both set `default = true`, GIVEN the user provides `--bfs-host` and no credential flag, THEN the CLI MUST exit non-zero and stderr MUST list the conflicting profile names. Add a `DELTA:CHANGED` block to `config/profiles` for the scenarios "Multiple default profiles is an error" and "Multiple profiles without default is an error", scoping each WHEN clause to "WHEN exapump resolves connection parameters from the config". Add a task to plan.md § Implementation Tasks that adds `bucketfs_host_override_reports_ambiguous_default_profile` to `tests/cli_test.rs`, and add the matching row to plan.md § Verification > Scenario Coverage. Update decision-log.md entry [2] to record the narrowed condition and the three distinct `find_default_profile` failures.

#### [COMPLETENESS_GAP] BLOCKER
- Location: plan.md § Design > Architecture (the five-branch diagram); plan.md § Implementation Tasks task 2.2
- Issue: the diagram lists `host, default profile resolves`, `host, no default profile`, and `no host, no default profile`. No branch matches "no `--bfs-host`, no `--profile`, and a default profile resolves". That combination is how `exapump bucketfs ls` runs today, and the spec delta requires it: bullet 3 of `cli/bucketfs-command-structure` § Background reads "Otherwise, the default profile is the base when one resolves". Task 2.2 instructs the implementer to implement "the five-branch precedence rule from the Architecture diagram", so plan.md and the spec delta disagree on the authoritative rule. A literal reading of the diagram routes today's default invocation to the branch-5 error. The regression ships unguarded: every test in `tests/bucketfs_test.rs` passes `--profile bfs`, `tests/cli_test.rs` holds only `bucketfs --help` assertions, and § Verification > Scenario Coverage has no row for an invocation with neither `--profile` nor `--bfs-host`.
- Fix: In plan.md § Design > Architecture, relabel branch 3 as `default profile resolves (with or without --bfs-host)` and branch 5 as `no default profile and no --bfs-host`. Add a sentence below the diagram stating that a run with no flag and a resolvable default profile keeps today's behavior. Add a `DELTA:NEW` scenario "Default profile stays the base when no override is given" to `cli/bucketfs-command-structure`, with GIVEN a config holding exactly one profile that sets `bfs_write_password`, GIVEN the user provides no `--profile` flag and no `--bfs-*` flag, THEN the base MUST be that profile. Add a task to plan.md § Implementation Tasks that adds `default_profile_lists_bucket_without_profile_flag` to `tests/bucketfs_test.rs`, and add the matching row to plan.md § Verification > Scenario Coverage.

#### [COMPLETENESS_GAP] ADVISORY
- Location: spec delta `cli/bucketfs-command-structure` § Scenarios, scenario "Self-sufficient overrides ignore the default profile"
- Issue: the scenario asserts the bucket and the port only. plan.md § Impact item 1 names `bfs_tls` and `bfs_validate_certificate` as the two fields whose new value breaks existing callers, and calls out `--bfs-validate-certificate false` as the required remedy. No scenario asserts that a self-sufficient override run enables certificate validation despite a profile that disables it. The single documented breaking change therefore has no pass/fail test.
- Fix: In the spec delta `cli/bucketfs-command-structure`, extend the scenario "Self-sufficient overrides ignore the default profile". Add `bfs_validate_certificate = false` to the profile in the first GIVEN, and add a final THEN reading "AND certificate validation MUST be enabled". Extend plan.md task 3.4 to assert the same field.

#### [REQUIREMENT_CONFLICT] ADVISORY
- Location: spec delta `config/profiles` § Scenarios, scenario "Read credential falls back to the --bfs-write-password flag"; decision-log.md entry [8]
- Issue: decision-log entry [8] is correct that the Basic-auth username is out of scope to fix. The recorded scenario `config/profiles/Read auth falls back to write_password` states "it MUST use `w:wp`", `src/commands/bucketfs.rs::list_bucket` sends `basic_auth("r", ...)`, and `docs/bucketfs.md` documents the code, not the spec. The plan leaves that unresolved and does not need to resolve it. The defect is elsewhere: the new scenario asserts only "the resolved read password MUST be `wp`" and names no username, so the merged library will hold two adjacent scenarios about one fallback with different observable requirements and no marker that one is known-wrong. The disagreement is recorded only in decision-log.md, which `/speq:record` archives with the plan and does not merge into the library.
- Fix: Add a `DELTA:CHANGED` block to the spec delta `config/profiles` for the recorded scenario "Read auth falls back to write_password". Keep its GIVEN and WHEN clauses. Replace the THEN clause with "THEN the resolved read password MUST be `wp`" and add "AND the Basic-auth username sent for the read is out of scope for this plan, tracked against the mismatch between `w:wp` and the `r` username that `BucketFsClient` sends". Add one sentence to plan.md § Design > Context naming that mismatch as a known open defect.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: plan.md § Design > Patterns; task 2.3; decision-log.md entry [4]
- Issue: after task 2.3, the rule "a write password can serve as a read credential" lives in two modules. `Profile::resolve_bfs_connection` in `src/config.rs` applies it to `bfs_write_password`, and `resolve_connection` in `src/commands/bucketfs.rs` applies it to `--bfs-write-password`. The Patterns table names a single owner for the BucketFS defaults and names no owner for this rule. The leak has a concrete cost that decision-log entry [4] runs into without naming: `BfsConnection.read_password` cannot distinguish an explicit `bfs_read_password` from one derived inside `resolve_bfs_connection`, which is the only reason entry [4] had to reject putting the flag ahead of the base read password. The resulting behavior surprises a caller. Given a profile with `bfs_write_password = "old"` and no `bfs_read_password`, the command `exapump bucketfs cp f dest --bfs-write-password new` writes with `new` and reads with `old`.
- Fix: Add a row to plan.md § Design > Patterns naming one owner for the write-to-read credential fallback. Extend task 1.1 to add `BfsConnection::effective_read_password(&self) -> Option<&str>` in `src/config.rs`, applying the fallback once over the merged connection. Rewrite task 2.3 to drop the fallback from `resolve_connection` and to call that method at the single read site. Record in decision-log.md entry [4] that the merged connection loses the distinction between an explicit and a derived read password, and name the stale-password case above as the known consequence.

## Prose Quality

#### [PROSE_UNCLEAR] ADVISORY
- Location: plan.md § Summary, sentence 2; plan.md § Design > Context, final sentence of paragraph 1; plan.md § Design > Consequences, row 2 Rationale
- Issue: three passages break `/speq:writing-guardrails`. First, "A caller that names a BucketFS host on the command line runs on a machine with no config file" reads as a claim about where callers run. It intends a requirement about what MUST work. - Fix: In plan.md § Summary, replace sentence 2 with "An override-only invocation MUST succeed on a machine with no config file." In plan.md § Design > Context, replace the final sentence of paragraph 1 with "The resolution order therefore never reaches the `--bfs-*` flags." In plan.md § Design > Consequences, replace the row-2 Rationale with "This branch fires only when the config holds zero profiles, so it replaces one error with a working connection and leaves every other profile-resolution error intact."
