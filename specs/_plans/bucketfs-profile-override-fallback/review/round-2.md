## Premortem

Three failure stories, written as if the revised plan already shipped and failed.

1. **The two new integration tests never went green.** Tasks 3.3 and 3.4 build a defaults base, and the defaults base enables certificate validation. The Exasol container presents a self-signed certificate. Neither task names `--bfs-validate-certificate false`, while every § Manual Testing command for the same behavior carries it. Routed to Feasibility as `[UNSTATED_ASSUMPTION]`.
2. **A CLI test reached a real BucketFS host.** Task 3.1 pins no `EXAPUMP_CONFIG`. On a machine with a real `~/.exapump/config.toml`, `exapump bucketfs ls` resolved that profile, tried to connect to the configured host, and failed with a connect error instead of the both-remedies message. Routed to Feasibility as `[UNSTATED_ASSUMPTION]`.
3. **A stale read password shipped.** After task 2.3 the write-to-read fallback lives in two modules. Given a profile with `bfs_write_password = "old"` and no `bfs_read_password`, `exapump bucketfs cp f dest --bfs-write-password new` wrote with `new` and read with `old`. Routed to Design Depth as `[INFORMATION_LEAKAGE]`.

#### [SCOPE_REDUCTION] ADVISORY
- Location: plan.md § Design > Context, the `**Goals**` bullet (line 18); plan.md § Impact (line 79)
- Issue: unfixed carry-over from round 1. The goal still reads "make an override-only BucketFS invocation succeed without a config file, and make it resolve to the same connection on every machine". The second half is false for a host-only run. Issue #46 states the secondary concern as "fields the caller didn't override (like `tls`/`validate_certificate`) silently inherit from that unrelated profile instead of using sane defaults". Branch 3 keeps that inheritance for `exapump bucketfs ls --bfs-host h`, and branch 4 uses the defaults base for the same command when the config holds zero profiles. The same command therefore still resolves to a different connection on two machines. Decision-log entry [1] justifies keeping the inheritance, so the decision is sound. The defect is that neither plan.md § Impact nor the `**Goals**` bullet states the resulting boundary.
- Fix: In plan.md § Design > Context, change the second goal to "make an override-only invocation that carries a BucketFS credential resolve to the same connection on every machine". Add one sentence to plan.md § Impact stating that a host-only run without a credential still inherits `bfs_tls`, `bfs_validate_certificate`, `bfs_bucket`, and `bfs_port` from an unrelated default profile, and that issue #46's secondary concern stays open for that case.

## Design Depth

#### [INFORMATION_LEAKAGE] ADVISORY
- Location: plan.md § Design > Patterns; plan.md § Implementation Tasks task 2.3; decision-log.md entry [4]
- Issue: unfixed carry-over from round 1. After task 2.3 the rule "a write password can serve as a read credential" lives in two modules. `Profile::resolve_bfs_connection` at `src/config.rs:59` applies it to `bfs_write_password`. `resolve_connection` in `src/commands/bucketfs.rs` will apply it to `--bfs-write-password`. The Patterns table names a single owner for the BucketFS defaults and names no owner for this rule. The leak has a concrete cost that decision-log entry [4] runs into without naming it: `BfsConnection.read_password` cannot distinguish an explicit `bfs_read_password` from one derived inside `resolve_bfs_connection`, which is the only reason entry [4] rejected putting the flag ahead of the base read password. The result surprises a caller. Given a profile with `bfs_write_password = "old"` and no `bfs_read_password`, the command `exapump bucketfs cp f dest --bfs-write-password new` writes with `new` and reads with `old`.
- Fix: Add a row to plan.md § Design > Patterns naming one owner for the write-to-read credential fallback. Extend task 1.1 to add `BfsConnection::effective_read_password(&self) -> Option<&str>` in `src/config.rs`, applying the fallback once over the merged connection. Rewrite task 2.3 to drop the fallback from `resolve_connection` and to call that method at the single read site. Record in decision-log.md entry [4] that the merged connection loses the distinction between an explicit and a derived read password, and name the stale-password case above as the known consequence.
